# 실제 배포 연동 작업 목록

대상: lily-dashboard + lily-frontend의 현재 실제 배포 연동. 이번 문서는 작업 분해이며 애플리케이션 코드는 변경하지 않는다.

## 현재 코드에서 확인한 사항

- 대시보드 `app/page.tsx`는 `NEXT_PUBLIC_APPS`로 목록을 만들고 `project` 쿼리를 읽지 않는다.
- `lib/api.ts`는 API 주소가 없으면 자동으로 mock을 사용하며, 앱 이름으로 관측 데이터를 요청한다.
- `Dashboard.tsx`는 첫 앱을 선택하고, 프로젝트 및 소유자 범위 없이 지표·로그·클러스터 서버를 조회한다.
- lily-frontend의 프로젝트 목록·상세 API는 `requireUser()`와 소유자 조건으로 보호된다. 이메일 인증도 검사한다.
- `Project`에는 `id`, `name`, `repo`, `rootDir`, `target`, `latestDeployment`가 있다. `latestDeployment`에는 상태·URL·실패 메시지·단계·빌드 로그가 있다.
- 실행기는 `builder_runs.app_name`에 실제 앱 이름을 저장한다. 프로젝트 조회 SQL과 응답 타입에는 빠져 있다. 대시보드에서 이름을 추측하거나 다시 생성할 필요가 없다.
- `database`는 프로젝트 생성 시 저장되지만 프로젝트 조회 SQL과 응답 타입에는 빠져 있다. 설정값과 실제 감지된 DB 종류를 구분할 계약이 필요하다.
- 꽃의 `GET /api/projects/:id/entry`는 최신 배포가 `succeeded`일 때만 진입 URL을 제공한다. 실패·진행 중인 배포의 대시보드 조회에는 일반 프로젝트 상세 API를 사용한다.

## Task 0 — 인증 연결과 배포 경로 확정

담당: 프런트/인프라 + 대시보드. 선행 조건: 없음.

- [ ] 권장안: 로그인 서비스와 대시보드를 같은 origin에서 서비스하고, `/dashboard` 같은 경로를 대시보드로 라우팅한다. 기존 인증 API와 프로젝트 API를 재사용한다.
- [ ] 별도 origin이 필요한 경우 서버에서 검증할 인증 연계 방식을 먼저 정의한다. URL의 프로젝트 ID만으로 인증하지 않는다.
- [ ] 대시보드 서버가 세션·프로젝트 검증 API를 호출하는 방식, 로그인/이메일 인증 경로와 돌아올 주소를 확정한다.
- [ ] 대시보드 URL과 내부 API 주소를 정하고 꽃의 `DASHBOARD_URL`을 맞춘다. 프로젝트와 배포 상태 응답은 사용자별로 처리하고 공유 캐시에 넣지 않는다.

완료 기준: 실제 배포 주소에서 로그인 세션을 대시보드 서버가 검증할 수 있으며, 로그인 후 원래 프로젝트 URL로 돌아온다.

## Task 1 — 프로젝트 → 실제 관측 대상 계약 확장

담당: lily-frontend의 서버 API/빌더 연동. 선행 조건: Task 0의 인증 경계 합의.

- [ ] 소유권을 확인한 프로젝트 응답에 서버에서 해석한 `appName`과 관측 대상 정보를 제공한다. 기존 `builder_runs.app_name`을 우선 사용한다.
- [ ] `projectId`를 공개 식별자로 유지하고, 앱 이름·클러스터/namespace·배포 위치·onprem 에이전트와의 매핑은 서버에서 관리한다. 프로젝트마다 데이터가 구분되도록 실제 수집 라벨도 확인한다.
- [ ] 최신 배포 시도와 현재 실행 중인 앱의 관측 대상을 구분한다. 새 배포 실패/롤백 뒤에도 기존 앱이 실행 중인 경우 그 관측 대상이 사라지지 않게 한다.
- [ ] 아직 빌더 실행 기록이 없는 프로젝트는 매핑 대기로 표현한다. 빈 이름을 레포 이름으로 대체하지 않는다.
- [ ] 필요 시 `database`를 프로젝트 응답에 추가한다. 미설정/감지 전과 명시적인 `none`을 구분하고, 실제 DB 사용 여부를 표시할 경우 빌더 결과도 반영한다.
- [ ] `Project`, `ReadyProject`, 프로젝트 변환 함수와 조회 SQL의 응답 계약을 함께 갱신한다. 환경변수 값과 에이전트 키는 응답에 포함하지 않는다.

주요 파일: lily-frontend `src/lib/projects/{server,types}.ts`, `src/lib/builder/worker.ts`와 프로젝트 API.

완료 기준: 본인 프로젝트 ID에서 실제 배포 관측 대상을 찾을 수 있고, 타인 프로젝트는 기존 404 정책에 따라 차단된다. 같은 레포의 다른 rootDir도 올바른 대상에 연결된다.

## Task 2 — 프로젝트 진입 및 서버 접근 보호

담당: 대시보드. 선행 조건: Task 0·1. 실제 프로젝트 진입 완성에는 Task 4도 필요.

- [ ] `app/page.tsx`에서 `?project=<UUID>`를 서버에서 읽고 검증한다. 잘못된 형식이나 중복 쿼리는 명시적으로 처리한다.
- [ ] 페이지를 렌더링하기 전에 세션·이메일 인증·소유권을 서버에서 확인하고 검증된 프로젝트 정보를 전달한다.
- [ ] 비로그인은 로그인으로, 미인증은 이메일 인증으로 안내한다. 삭제되었거나 접근할 수 없는 프로젝트를 임의의 첫 프로젝트로 대체하지 않는다.
- [ ] project가 없는 직접 접근은 인증된 내 프로젝트 목록/선택 화면으로 연결한다.
- [ ] 실패·진행 중·배포 전 프로젝트도 본인에게는 상세 상태를 제공한다. 꽃의 성공 전용 entry API를 모든 대시보드 조회의 조건으로 쓰지 않는다.
- [ ] 클라이언트의 선택 기준을 앱 이름에서 프로젝트 ID로 변경한다. 새로고침/직접 링크에도 같은 프로젝트를 선택한다.

주요 파일: `app/page.tsx`, `components/Dashboard.tsx`, 새 서버 조회 모듈.

완료 기준: 꽃의 URL 진입과 직접 URL 진입에 동일한 서버 보호가 적용되고, 인증 및 프로젝트 검증 전에는 관측 요청이 시작되지 않는다.

## Task 3 — 사용자별 프로젝트 목록과 선택 전환

담당: 대시보드. 선행 조건: Task 1·2.

- [ ] `NEXT_PUBLIC_APPS` 대신 인증된 프로젝트 목록 API를 사용한다. 목록이 여러 페이지면 페이지 이동 또는 추가 로딩을 제공한다.
- [ ] 선택 항목에 표시 이름·레포·rootDir·cloud/onprem 정보를 보여준다. 동일 이름이어도 프로젝트 ID로 구분한다.
- [ ] 선택 변경을 URL의 project 값과 동기화하고 뒤로/앞으로 이동을 처리한다.
- [ ] 쿼리 키에 프로젝트 ID와 관측 대상 범위를 포함한다. 필터를 초기화하고 이전 프로젝트 요청·데이터가 새 프로젝트 화면에 남지 않게 한다.
- [ ] 세션 만료/로그아웃 때 폴링을 중단하고 사용자 캐시를 정리한다. 프로젝트가 없는 사용자도 처리한다.

주요 파일: `components/{Dashboard,TopBar}.tsx`, `lib/types.ts`.

완료 기준: 같은 레포의 두 rootDir 프로젝트를 번갈아 선택해도 화면과 요청 대상이 정확히 바뀌고 다른 프로젝트의 데이터가 섞이지 않는다.

## Task 4 — 실데이터 모드와 데이터 가용 상태 분리

담당: 대시보드. 선행 조건: 없음. Task 0·1과 병행 가능.

- [ ] 실제 프로젝트 진입은 API 주소가 없어도 mock으로 넘어가지 않는다. 공개 mock 설정이 켜져 있어도 실제 project 진입에는 적용하지 않는다.
- [ ] 데모는 별도 명시적 진입으로 분리하고 화면에도 표시한다.
- [ ] 연결 설정 필요, 앱 매핑 대기, 수집 대기, 수집 미지원, 표본 부족, 요청 오류를 구분한다. 0%·0ms를 가짜 기본값으로 사용하지 않는다.
- [ ] 관측 대상이 확인된 뒤에만 쿼리를 활성화한다. 상태별 재시도와 폴링 정책을 정한다.
- [ ] HTTP 상태와 서버 오류 코드를 보존해 인증 오류와 수집 실패를 구분한다.

주요 파일: `lib/api.ts`, `lib/types.ts`, `components/Dashboard.tsx`, `.env.example`.

완료 기준: 실제 project URL에서 API 미설정·장애·수집 대기 상황 모두 데모 수치가 나타나지 않는다.

## Task 5 — 프로젝트 범위 관측 API 연결

담당: 서버 API/모니터링 + 대시보드. 선행 조건: Task 0·1·2·4.

- [ ] 제안 경로: `GET /api/projects/:id/metrics`, `/logs`, `/servers`. 기존 프로젝트 경로와 충돌 여부는 Task 0에서 확정한다. 현재 이미 존재하는 API라는 뜻은 아니다.
- [ ] 모든 경로가 매 요청마다 세션·소유권을 확인하고 프로젝트의 서버 매핑으로 Observability API를 호출한다. 브라우저가 임의의 appName이나 에이전트를 지정해 조회할 수 없게 한다.
- [ ] 클러스터 전체 노드 정보의 노출 범위를 정한다. 앱 자원인지, 할당된 서버인지, 허용된 공용 클러스터 정보인지 구분한다.
- [ ] cloud/onprem 수집 대상과 수집 지원 여부를 서버에서 선택한다.
- [ ] 현재 요청 수·에러율·p95 그래프와 실행 로그를 새 경로에 연결한다. 버전·트래픽 역할은 실제 관측 결과를 사용한다.
- [ ] 실데이터의 nullable 값, 요약/시계열 구간, 오류 판정, 로그 수준·페이지네이션 계약을 갱신한다. 수집기 인증정보는 서버에 둔다.

주요 파일: 새 서버 Route Handlers/관측 어댑터, `lib/api.ts`, `lib/types.ts`, `docs/api-contract.md`.

완료 기준: 올바른 프로젝트의 실데이터가 기존 패널에 나타나며, 관측 API 직접 호출로도 다른 소유자의 데이터에 접근할 수 없다.

## Task 6 — 배포 상태와 빌드 로그 패널

담당: 대시보드. 선행 조건: Task 1·2·4. 관측 API 준비와 병행 가능.

- [ ] 기존 latestDeployment의 상태·실제 단계·URL·실패 메시지를 표시한다. 배포 전 상태도 처리한다.
- [ ] 현재 API가 제공하는 빌드 로그 끝부분을 표시한다. 전체 로그/배포 이력이 필요하면 별도 조회 계약을 추가한다.
- [ ] 빌드 로그와 실행 중인 앱 로그를 분리한다. 운영 상태와 최신 배포 시도의 상태도 구분한다.
- [ ] 진행 중인 배포를 폴링하고, 종료 상태에서는 폴링 주기를 조정한다. 서버 단계가 없으면 추측한 진행률 대신 대기를 표시한다.
- [ ] 3D 공간과 목록 보기에서 같은 배포 정보를 제공한다. 패널을 추가하거나 기존 패널을 확장할 배치를 정한다.

주요 파일: 새 배포 패널, `Dashboard.tsx`, `TopBar.tsx`, `ParticleStage.tsx`, 프로젝트 타입.

완료 기준: 진행 중·성공·실패·롤백 상태의 정보가 표시되고, 지표 수집이 준비되지 않아도 배포 상태와 빌드 로그는 볼 수 있다.

## Task 7 — 내 PC 관측 가용성과 환경 표시

담당: 서버 API/모니터링 + 대시보드. 선행 조건: Task 1·4·5의 대상 분기 계약.

- [ ] cloud/onprem을 프로젝트 응답으로 식별하고 화면에 표시한다.
- [ ] onprem의 에이전트 연결 여부와 지표 수집 지원 여부를 구분한다. 에이전트가 연결됐다고 지표 수집이 지원되는 것은 아니다.
- [ ] 수집 API가 없는 내 PC는 미지원, 지원하지만 첫 데이터가 없는 경우 대기 상태를 표시한다.
- [ ] 내 PC 프로젝트에 클라우드 노드 지표를 대신 보여주지 않는다. 배포 정보·빌드 로그는 별도로 계속 제공한다.

완료 기준: 내 PC 수집이 미지원이어도 사용자가 대상 환경과 현재 가능한 기능을 알 수 있으며 가짜 수치가 나타나지 않는다.

## Task 8 — 전체 진입 흐름 검증

담당: 대시보드 + 프런트/서버. 선행 조건: Task 0–7.

- [ ] 꽃 → project URL → 서버 인증 → 실제 앱 매핑 → 지표/로그 표시.
- [ ] 직접 URL·비로그인·이메일 미인증·만료 세션·타인 UUID·삭제된 프로젝트·잘못된 UUID.
- [ ] 관측 API 직접 호출과 로그 cursor/필터 변경에도 소유권 보호 유지.
- [ ] 같은 레포/다른 rootDir 전환, 목록 페이지 이동, URL 뒤로가기, 전환 중 늦게 도착한 응답.
- [ ] 배포 전/진행 중/성공/실패/롤백, 최신 시도 실패 후 기존 앱 유지, 앱 매핑 대기.
- [ ] API 미설정·수집 대기·표본 부족·서버 오류·onprem 미지원에 데모 값이 섞이지 않음.
- [ ] 실제 배포 주소에서 인증 전달과 로그인 복귀 확인. 모바일·목록·3D 패널의 표시와 조작 유지.

완료 기준: 위 시나리오를 검증하고 어떤 경우에도 데이터 범위가 프로젝트/사용자 경계를 넘지 않는다.

## 권장 진행 순서

1. **첫 묶음:** Task 0·1·2·4. 인증된 실제 프로젝트에 진입하고 매핑 결과/연결 대기를 표시하는 지점까지 완성한다.
2. **두 번째 묶음:** Task 3 + Task 5·6 병행. 프로젝트 전환, 실제 관측, 배포 정보 표시를 연결한다.
3. **마지막 묶음:** Task 7·8. 내 PC 상태와 실제 배포 환경의 전체 검증을 마무리한다.

배포 API는 이미 있어서 Task 6은 관측 API 완성을 기다리지 않고 진행할 수 있다. 현재 꽃·360도 카메라·패널 추종은 그대로 활용한다.

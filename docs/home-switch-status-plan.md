# 클라우드 ↔ 온프레미스 전환 상태 표시 계획

작성일: 2026-10-03. 이 문서는 계획이며 아직 구현하지 않았습니다.

**원칙: 기존 대시보드에 붙어 있는 패널·버튼·문구는 지우지 않고 추가만 합니다.** 여섯 패널 구성(지표·추이·배포 비교·서버·로그·거점과 트래픽)도 유지합니다.

## 1. 확인 결과

### 로컬에서 사라진 것인가

아닙니다. 로컬과 원격 모두 코드가 남아 있습니다.

| 위치 | 상태 |
|---|---|
| lily-frontend 로컬 (`feature/ai-fix-progress`) | 전환 관련 컴포넌트 `StatusOverview`·`BurstPanel`·`ActivityProgress`·`MovePanel`·`PlaceBadge`가 모두 있음 |
| lily-frontend `origin/main` | 위와 같음. 전환 관련 브랜치 7개(`기능/지금-상태-표시`, `기능/버스트-거점-진행표시`, `기능/클라우드-온프레-전환` 등)는 모두 main에 머지됨 |
| lily-monitoring-dashboard 로컬 | `origin/main`(`535ce2a`)과 같음. `TrafficPanel`(거점과 트래픽)이 있음 |

참고: frontend `3d4d00c`(2026-10-02)는 버스팅 조작을 **계정 화면에서 빼낸** 커밋입니다. 같은 기능은 지금 `/projects/[id]`의 `ProjectMonitor`에 있습니다.

### 대시보드에 안 보이는 이유

1. **로컬 프로젝트가 모두 클라우드 프로젝트입니다.** 로컬 DB의 `lily-blog-sample`과 `nextjs`가 모두 `target=cloud`입니다.
   - frontend는 `target=onprem`이고 앱 이름이 있을 때만 `burst`(거점·버스팅 상태)를 채웁니다(`src/lib/projects/server.ts`의 `burstable`).
   - 대시보드 `TrafficPanel`은 `target !== 'onprem'`이면 "온프레미스로 배포한 프로젝트에서 거점 전환과 클라우드 버스팅을 관리할 수 있어요." 안내만 보여 줍니다.
2. **클라우드 → 내 PC 옮기기는 진행 중에 대시보드에 나타나지 않습니다.**
   - 옮기는 동안 프로젝트는 아직 `target=cloud`이고, 배포 기록의 `latestDeployment.move === "onprem"`으로만 구분됩니다.
   - 대시보드는 `move`를 읽지 않습니다. 끝나면 `target`이 `onprem`으로 바뀌어(`src/lib/builder/worker.ts:311`) 그때부터 거점 패널이 나옵니다.
3. **온프레미스 프로젝트여도 frontend 상세보다 정보가 적습니다.** 아래 §2의 차이입니다.

### 데이터는 이미 옵니다

대시보드가 쓰는 `GET /api/projects/{id}` 응답에 아래 값이 이미 들어 있습니다. 대시보드 타입(`lib/project.ts`)에 없어서 읽지 않을 뿐입니다. **frontend API를 바꿀 필요는 없습니다.**

- `burst.live.homeStepSince`, `burst.live.phaseSince`
- `burst.builds.homeBuild`, `burst.builds.standbyBuild` (상태·마지막 로그 줄)
- `movedFromCloud`
- `latestDeployment.move` (`"onprem" | null`)

## 3. 구현 방향

- **위치**: 새 패널을 만들지 않습니다. "거점과 트래픽" 패널과 "배포 비교" 패널 안에 추가합니다.
- **로직**: frontend `src/lib/projects/burst.ts`의 `activities()`, `homeStepLabels`, `elapsed()`, `overview()`를 대시보드 `lib/switch.ts`로 옮깁니다.
  - 파일 머리에 출처(frontend 커밋 SHA)를 적고, frontend `burst.test.ts`의 같은 경우를 테스트로 옮깁니다.
  - 두 레포는 따로 배포되므로 이번에는 복사합니다. 공통 패키지로 묶는 것은 별도 작업입니다.
- **문구**: frontend와 같은 한국어 원문을 키로 쓰고 `lib/i18n/en.json`·`ja.json`에 번역을 추가합니다.
- **기존 요소 유지**: 이미 있는 "진행 단계:" 줄, 전환·버스팅 버튼, 안내 문구는 그대로 둡니다. 새 블록은 그 아래에 붙입니다.

## 5. 검증

- **로컬 데이터 한계**: 로컬 DB에는 온프레미스 프로젝트가 없습니다. 실제 화면 확인에는 다음 중 하나가 필요합니다.
  - 내 PC 에이전트(lily-on-premise)를 연결하고 온프레미스 프로젝트를 하나 배포하기
  - 클라우드 프로젝트를 "클라우드 → 온프레미스 전환"으로 옮기기 (S6 확인도 겸함)
- **자동 테스트**: `lib/switch.ts`는 frontend와 같은 입력·기대값의 단위 테스트로 확인합니다. 화면은 응답 예시(전환 중 각 단계, 대기 배포 중, 옮기는 중, 옮긴 뒤, 에이전트 끊김)를 넣어 렌더링을 확인합니다.
- **회귀 확인**: 기존 여섯 패널, 전환·버스팅 버튼, 기존 안내 문구가 그대로 있는지 확인합니다.

## 6. 결정이 필요한 것

1. **"진행 단계:" 줄**: 지금은 `DNS` 같은 원래 코드를 보여 줍니다. 기존 줄을 유지하면서 새 블록과 정보가 겹칩니다. 그대로 둘지, 단계 이름으로만 바꿀지 정해 주세요. 기본안은 "그대로 두기"입니다.
2. **로직을 복사할지 공유할지**: 이번에는 복사를 권합니다. frontend API가 계산된 진행 상태를 내려주게 바꾸면 중복은 없어지지만, 두 앱을 같이 배포해야 합니다.
